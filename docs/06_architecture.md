## 1. 한눈에 보기

### 1.1 구성

```
[브라우저]  화면 (HTML, CSS, JavaScript)
    │   ├─ 입력한 값 보관: 브라우저 저장소
    │   └─ 지도 그리기: 카카오맵 스크립트 ────────→ [카카오맵]
    │
    │   (1) 화면 파일 받기      (2) /api 요청과 응답 (JSON)
    ▼
[서버]  FastAPI, 8000번 포트
    │   ├─ 화면 파일을 내준다
    │   └─ API: 값 검사 → 계산 → DB 조회와 저장
    ▼
[DB]  MariaDB 11.4, 표 8개
    ▲
    │   팀이 직접 실행한다. 서버와는 따로 돈다.
[수집 스크립트] ←── 실거래가 (API 또는 CSV), 카카오 좌표 변환, 공급면적 CSV, 세대수 자료
```

### 1.2 부분별 역할

| 부분 | 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| 화면 | 입력받기, 서버가 준 값 보여 주기, 지도 그리기, 입력한 값을 브라우저에 보관 | 계산. 계산식을 화면에 두지 않는다. |
| 서버 | 값 검사, 계산, DB 조회와 저장, 로그인 확인 | 요청을 처리하는 중에 외부 API를 부르는 일 |
| DB | 아파트와 거래, 대출 상품, 회원의 값 보관 | 계산 결과 보관. 저장한 결과(3차)만 예외다. |
| 수집 스크립트 | 실거래를 받아 정리해 DB에 넣기, 주소를 좌표로 바꾸기 | 사용자의 요청에 답하는 일. 팀이 필요할 때 손으로 실행한다. |
| 카카오맵 | 지도 그림, 로드뷰(3차), 주변 시설(3차) | 우리 자료 보관. 아파트의 위치는 우리 DB에 있다. |

### 1.3 왜 이렇게 나눴는가

- **화면과 서버를 한 주소(8000번)로 낸다.** 주소가 하나면 브라우저의 출처 제한을 따로 풀 필요가 없고, 로그인 쿠키도 그대로 오간다. 카카오맵에 등록할 주소도 하나다.
- **계산을 서버의 한 파일에 모은다.** 지도, 목록, 시나리오가 같은 숫자를 보여야 한다. 계산이 여러 곳에 있으면 한 곳만 고쳐도 숫자가 어긋난다 (NFR-13).
- **자료 수집을 서버와 떼어 놓는다.** 사용자가 지도를 볼 때마다 공공 API를 부르면 느리고 호출 한도에 걸린다. 미리 받아 DB에 넣어 둔다 (NFR-08).

## 2. 기술 스택

| 구분 | 기술 | 쓰는 곳 | 상태 |
| --- | --- | --- | --- |
| 화면 | HTML, CSS, JavaScript. Bootstrap, Sass, React 같은 라이브러리와 프레임워크는 쓰지 않는다. | 화면 전체 | 확정 (2026-10-12) |
| 지도 | 카카오맵 JavaScript SDK | 지도 화면 | 확정 |
| 서버 | Python 3.12, FastAPI, Uvicorn | API, 화면 파일 제공 | 확정 |
| 값 검사 | Pydantic (FastAPI에 들어 있다) | 요청의 모양과 범위 검사 | 확정 |
| DB | MariaDB 11.4. 개발 도구는 HeidiSQL | 자료 보관 | 확정 |
| 자료 처리 | Pandas | 수집 스크립트 | 확정 |
| DB 접근 | SQLAlchemy 2. 접속은 PyMySQL이 한다. 수집·적재 스크립트만 SQL을 직접 쓴다. | 서버 | 확정 (T-2, 2026-10-13에 바꿈) |
| 로그인 | 서명한 쿠키, bcrypt | 2차의 회원 기능 | 확정 (T-3) |
| 테스트 | pytest | 계산 모듈의 자동 테스트 | 권장 |
| 설정 | python-dotenv, `.env` | 키와 DB 접속 정보 | 권장 |

- 라이브러리의 버전은 `requirements.txt`에 적어 네 명이 같은 버전을 쓴다.
- 라이브러리는 프로젝트 폴더의 가상 환경(`.venv`)에 설치한다. PC의 다른 Python과 섞이지 않는다.
- 기획서와 명세서의 기술 목록에 있는 Matplotlib은 3차의 변동 그래프에서만 쓸 수 있다. 그리는 방법이 정해지지 않았다 (N-07).

## 4. 서버의 구조

### 4.1 네 층

| 층 | 파일 | 하는 일 | 규칙 |
| --- | --- | --- | --- |
| 받는 곳 | `routers/`, `schemas/` | 요청을 받고, 값을 검사하고, 응답을 만든다. | DB를 다루는 코드와 계산식을 쓰지 않는다. `services`를 부르기만 한다. |
| 일하는 곳 | `services/` (계산 모듈 제외) | DB에서 읽고 쓴다. 규칙을 확인한다. | `select(...)`는 여기에만 쓴다. `commit`하지 않는다. |
| 계산 | `services/calc.py` | 숫자를 받아 숫자를 돌려준다. | DB를 모른다. 요청도 모른다. 그래서 DB 없이 테스트할 수 있다. |
| 자료 | `database.py`, `models/` | 표를 클래스로 옮겨 둔다. 세션을 내준다. | 표는 `db/schema.sql`로 만든다. 클래스는 그 표에 맞춘다. |

### 4.2 요청 하나가 지나가는 길

지도에서 아파트를 찾을 때(A-05)를 예로 든다.

```
화면 ── POST /api/apartments/search ──→ routers/apartments.py
                                          1. schemas로 값을 검사한다. 틀리면 422로 답한다.
                                          2. DB에서 대출 상품 한 줄을 읽는다.
                                          3. DB에서 범위 안의 아파트와 면적별 평균가를 읽는다.
                                          4. 면적마다 services/calc.py를 불러 대출금액, 구분, 부족자금을 계산한다.
                                          5. 아파트의 구분을 정하고, 순서대로 줄 세우고, 개수를 센다.
화면 ←── 응답 (JSON) ─────────────────── 6. 응답을 만든다.
```

### 4.3 계산 모듈의 함수 (제안)

계산 규칙마다 함수 하나다. 이름은 제안이다.

| 함수 | 규칙 | 받는 값 | 돌려주는 값 |
| --- | --- | --- | --- |
| `accumulated_saving` | C-02 | 월 저축 가능액, 목표 연수 | 누적 저축액 |
| `own_funds` | C-03 | 현재 보유자산, 누적 저축액 | 목표 시점 자기자금 |
| `loan_amount` | C-05, C-13 | 평균가, 상품(없으면 대출 없이 계산) | 예상 대출금액 |
| `max_loan_amount` | C-06 | 현재 보유자산, 상품 | 최대 예상 대출금액 |
| `monthly_payment` | C-07 | 대출금액, 연 금리, 상환 연수 | 예상 월 상환액 |
| `target_price` | C-08, C-13 | 자기자금, 상품 | 목표 가능 가격 |
| `category` | C-09 | 현재 보유자산, 자기자금, 대출금액, 평균가, 목표 연수 | `now`, `within`, `lack` |
| `shortage` | C-10 | 평균가, 자기자금, 대출금액 | 부족자금. 음수면 여유자금 |
| `required_monthly_saving` | C-11 | 평균가, 대출금액, 현재 보유자산, 목표 연수 | 필요 월 저축액 또는 없음 |
| `allowed_growth_rate` | C-12 | 목표 가능 가격, 평균가, 목표 연수 | 허용 상승률 또는 없음 |

- 금액은 모두 원 단위 정수로 받고 돌려준다 (NFR-12). 버림, 반올림, 올림은 명세서 부록 C를 따른다.
- 이 파일을 **가장 먼저** 만들고 테스트를 붙인다. API 여섯 개(A-03, A-04, A-05, A-07, A-12, A-21)가 이 파일에 기댄다.
- 테스트에는 정상값, 경계값(0원, 목표 기간 "지금", 최대 한도 초과, 대출 없이 계산), 손으로 계산한 사례 5건 이상을 넣는다 (NFR-03). 와이어프레임과 API 명세서의 예시 값을 그대로 쓸 수 있다.

### 4.4 서버가 지키는 규칙

| 규칙 | 지키는 방법 | 근거 |
| --- | --- | --- |
| 계산식은 한 곳에만 | `services/calc.py` 밖에 계산식을 쓰지 않는다. | NFR-13 |

## 5. 화면의 구조

### 5.1 파일

- 화면마다 HTML 파일 하나를 둔다. 화면 사이는 주소를 옮겨 이동한다.
- 아래 창(P-06)은 따로 파일을 두지 않고 `map.html` 안에 있다.
- 공통 JavaScript 다섯 개를 모든 화면이 먼저 불러 쓴다.

| 파일 | 하는 일 | 근거 |
| --- | --- | --- |
| `api.js` | 서버를 부르는 함수 하나. 응답이 오류면 `detail`과 `field`를 꺼내 준다. 401이면 시작 화면으로 보낸다. | T-COMMON-04, FR-USER-08 |
| `store.js` | 입력한 값과 보던 자리를 브라우저 저장소에 읽고 쓴다. | FR-PROFILE-11 |
| `format.js` | "3억 2,500만 원", "111㎡ (전용 84㎡)", 평 환산 | FR-COMMON-11, FR-APT-13, 14 |
| `guard.js` | 계산에 필요한 값이 빠졌으면 빠진 첫 단계로 보낸다. | FR-RESULT-10 |
| `layout.js` | 화면의 공통 틀을 그린다. 모바일에는 헤더가 없으므로(확정 목업 v3) 지금은 그릴 것이 없다. 웹 배치의 틀이 정해지면 여기에 둔다. | FR-COMMON-04 |

### 5.2 브라우저에 보관하는 값

탭을 닫을 때까지 남는 저장소(sessionStorage)에 둔다. 값의 이름은 API와 DB의 이름과 같게 한다.

| 묶음 | 담는 값 | 쓰는 화면 |
| --- | --- | --- |
| 입력 | 만 나이, 연 소득, 현재 보유자산, 대출 방법과 상품과 상환 기간, 월 저축 가능액, 목표 기간 | 전체 |
| 자리 | 보던 단계와 질문, "처음부터 다시 입력"을 골랐는지 | 입력 화면 |
| 지도 | 구와 동, 조건, 정렬, 면적 단위, 자금 부족 표시, 지도의 가운데와 확대 수준 | 지도 |

- 금액은 원 단위로 보관한다. 만원으로 받은 값에 10,000을 곱해 넣는다.
- **주민등록번호는 넣지 않는다.** 만 나이만 넣는다 (NFR-25).
- 묶음마다 저장소의 칸 하나에 통째로 넣는다. 네 명이 각자 칸을 만들면 화면이 이어지지 않으므로, `store.js`의 함수로만 읽고 쓴다.

### 5.3 지도 화면

일이 가장 많은 화면이라 파일을 기능별로 나눈다.

| 파일 (제안) | 하는 일 |
| --- | --- |
| `map-state.js` | 지금 조건, 찾은 결과, 고른 아파트와 면적, 창의 단계를 한곳에 둔다. |
| `map-view.js` | 지도 띄우기, 아파트 표시와 구·동 표시 그리기, 지도 이동 |
| `sheet.js` | 아래 창의 세 단계, 열고 닫기, 끌기 |
| `list.js` | 목록과 카드, 정렬, 면적 넘기기 |
| `apartment.js` | 아파트 창의 탭, 아파트 정보, 시나리오, 다시 계산 |

- 표시, 카드, 창이 같은 아파트를 가리켜야 한다. 고른 아파트는 `map-state.js` 한곳에만 두고 나머지는 그것을 읽는다.
- 서버나 DB에서 온 글자를 화면에 넣을 때는 HTML로 해석되지 않는 방법으로 넣는다 (NFR-20).

## 6. 자료 준비

수집과 적재는 서버와 따로 도는 스크립트다. 팀이 필요할 때 실행한다. 순서와 규칙은 DB 설계서 5장에 있다.

| 순서 | 스크립트 | 하는 일 | 쓰는 키 | 단계 |
| --- | --- | --- | --- | --- |
| 1 | `db/schema.sql` | 표 8개를 만든다. | | 1차 |
| 2 | `db/seed_loan_products.sql` | 대출 상품 두 줄을 넣는다. 조사(R-01, R-02)한 실제 조건이다. 금리가 바뀌면 이 파일의 값과 기준일을 함께 바꾼다. | | 1차 |
| 3 | `data/load_trades.py` | 실거래 CSV를 읽어 아파트, 거래, 면적별 평균가, 공급면적을 넣는다. | | 1차 |
| 4 | `data/geocode.py` | 아파트 주소를 좌표로 바꿔 넣는다. 실패한 곳은 기록한다. | 카카오 REST API 키 | 1차 |
| 5 | `data/collect_trades.py` | 실거래가 API로 받아 3번과 같은 표에 넣는다. | 공공데이터 인증키 | 2차 |
| 6 | `data/load_households.py` | 세대수를 붙인다. | | 2차 |

- 1차는 이미 갖고 있는 CSV로 시작한다. API 수집은 2차에 붙인다. 두 방법이 같은 표에 들어가므로 서버와 화면은 차이를 모른다.
- 3번은 설계할 때 시험으로 한 번 돌려 보았다. 아파트 1,054곳, 거래 16,919건, 평균가 1,848줄이 들어갔다.
- 4번은 아직 해 보지 않았다. 좌표가 없으면 지도에 아무것도 나오지 않으므로 **지도 화면을 만들기 전에 끝나야 한다.**
- 화면을 먼저 만들 수 있게 예시 자료 10건을 따로 준다 (T-DATA-09).

## 7. 설정과 비밀 값

키와 비밀번호는 `.env` 파일에만 둔다. 이 파일은 Git에 올라가지 않는다. 팀원에게는 Git이 아닌 방법으로 전한다.

## 8. 로그인과 보안

### 8.1 1차: 로그인 없음

- 로그인 기능이 없다. 재무정보를 저장하는 API(A-08 ~ A-11)는 테스트 사용자 한 명(번호 1)의 값을 읽고 쓴다 (T-USER-08).
- "지금 사용자가 누구인가"를 알아내는 함수를 `deps.py`에 하나만 둔다. 1차에는 이 함수가 늘 1을 돌려준다. 2차에 이 함수만 고치면 로그인이 붙는다.

### 8.2 2차: 로그인

| 항목 | 방법 | 근거 |
| --- | --- | --- |
| 로그인 상태 | 서명한 쿠키에 회원 번호를 담는다. 서버는 로그인 상태를 따로 저장하지 않는다. 그래서 표가 필요 없다. | NFR-04, DB 설계서 D-5 |

| 비밀번호 | bcrypt로 해시해 저장한다. 원래 값은 남기지 않는다. | FR-USER-14 |
| 본인 자료만 | 누구의 자료인지는 쿠키의 회원 번호로만 정한다. 요청에 든 번호를 믿지 않는다. | FR-USER-15 |
| 로그인이 필요한 API | 쿠키가 없거나 수명이 지났으면 401로 거부한다. | NFR-10 |

## 9. 실행과 협업

### 9.1 처음 한 번 하는 준비

1. Python 3.12와 MariaDB 11.4를 설치한다.
2. 저장소를 내려받는다.
3. `python -m venv .venv`로 가상 환경을 만들어 켜고, `pip install -r requirements.txt`로 라이브러리를 설치한다.
4. `.env.example`을 복사해 `.env`를 만들고 값을 채운다.
5. HeidiSQL에서 `db/schema.sql`과 `db/seed_loan_products.sql`을 실행한다.
6. 6장의 2 ~ 4번 스크립트로 자료를 넣는다.

### 9.2 실행

```
uvicorn backend.main:app --reload --port 8000
```

브라우저에서 `http://localhost:8000`을 연다. 화면과 API가 같은 주소로 나온다. 자동 테스트는 `pytest`로 돌린다.

### 9.3 누가 어느 파일을 맡는가 (제안)

담당은 2026-10-12에 정했다. 네 명 모두 화면, 서버, DB를 다 쓴다. 할 일의 순서는 `docs/roles.md`에 있다.

| 담당 | 화면 | 서버 | 그 밖 |
| --- | --- | --- | --- |
| 김해원 (팀장). 입력과 공통 | `index.html`, `profile.html`, `plan.html`, `common.css`, 공통 JavaScript 다섯 개 | `main.py`, `config.py`, `database.py`, `deps.py`, `errors.py`, `routers/profile.py`, `routers/plans.py`, `routers/system.py`, `models/`의 여덟 파일, `services/profile.py`, `schemas/common.py`, `schemas/profile.py` | `requirements.txt`, `CLAUDE.md`, 문서, PR 검토와 통합 점검 |

- 자기 파일만 고친다. 남의 파일을 고쳐야 하면 담당에게 먼저 말한다.
- `main.py`에는 새 router를 등록하는 한 줄만 더한다.

### 9.4 만드는 순서

뒤의 것이 앞의 것에 기댄다.

| 순서 | 만드는 것 | 이유 |
| --- | --- | --- |
| 1 | 표 만들기와 자료 넣기, 좌표 변환 | 자료가 없으면 지도와 목록을 볼 수 없다. |
| 2 | 계산 모듈과 테스트 | API 여섯 개가 기댄다. |
| 3 | 서버의 틀(`main.py`, 오류 처리)과 화면의 공통 파일 | 네 명이 같은 틀 위에서 만든다. |
| 4 | 화면과 API를 담당별로 | 각자 자기 파일만 고친다. |
| 5 | 이어 붙여 점검 | 재무정보 입력부터 시나리오까지 처음부터 끝까지 해 본다 (NFR-22). |

- 공통 파일은 한 사람이 먼저 만들어 `develop`에 올리고, 나머지가 그 위에서 시작한다. 여러 명이 같은 파일을 동시에 고치면 합칠 때 충돌한다.
- 화면 담당은 API가 다 만들어지기를 기다리지 않는다. API 명세서의 예시 응답을 파일로 두고 먼저 만든다.

| 9 | 네 명의 개발 환경이 다르다. | 한 PC에서 되는 것이 다른 PC에서 안 된다. | 버전을 `requirements.txt`에 적고, 표는 스크립트로만 만든다. |
| 10 | 발표할 때 어디서 돌릴지 정하지 않았다. | 다른 곳에 올리면 주소 등록, 쿠키 설정, 위치 권한이 달라진다. | 지금은 PC에서 돌리는 것을 기준으로 한다. 올리기로 하면 11장의 T-7을 다시 본다. |

여섯 가지 모두 첫째 선택지(권장안)로 정했다. 이 문서는 그대로 쓰여 있다.

| T-1 | 화면 파일을 누가 내주는가 | FastAPI가 함께 낸다. | 주소가 하나라 출처 제한과 쿠키 설정이 필요 없다. 실행 명령도 하나다. |

| T-3 | 로그인 상태를 어디에 두는가 | 서명한 쿠키 | 표와 정리 작업이 필요 없다. 명세서에 이미 "세션 서명 키"가 있다. |

| T-5 | 화면 파일을 어떻게 나누는가 | 화면마다 HTML 하나 | 담당별로 파일이 나뉘어 충돌이 적다. |
| T-6 | 표를 만드는 스크립트의 자리 | `db/schema.sql`로 옮겼다. | 문서 폴더에는 문서만 둔다. |

T-2는 2026-10-13에 바꿨다. 강사님의 수업 자료(10월 13일, "SQLAlchemy Model 생성")에 따라 SQL을 직접 쓰던 것을 SQLAlchemy로 바꿨다. 표는 여전히 `db/schema.sql`로 만든다. T-3은 수업에서 정해 준 방법이 있으면 그것이 먼저다 (T-8).
