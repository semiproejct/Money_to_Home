## 1. 평균가 기간이 13개월로 잡힘

- **발생 일시:** 2026-10-13
- **담당자:** 김목산
- **영향 범위:** 아파트 평균가 1,852줄 전체, 그 평균가로 계산하는 구분 · 부족자금

### 문제 상황

- 실거래 수집과 평균가 계산의 기간이 서로 달라, 화면의 "최근 1년 거래" 건수와 평균가가 설명과 맞지 않았습니다.
- 사용자는 1년보다 오래된 거래가 섞인 평균가를 보게 됩니다.
- 오류 메시지는 없었습니다. 적재 결과의 기간(`period_start` ~ `period_end`)을 보고 발견했습니다.

### 원인 분석

- **직접 원인:** 평균을 내는 기간이 13개월로 잡혀 있었고, 수집 기간과 평균 기간이 서로 달랐습니다.
- **근본 원인:** "최근 1년"이 정확히 어느 달부터 어느 달까지인지 요구사항에 숫자로 정해 두지 않았습니다.
- **확인 방법:** `apartment_prices`의 `period_start` · `period_end`와 `trades`의 `MIN/MAX(contract_date)`를 비교했습니다.

### 해결 과정

1. 기간을 **"지난달까지 12개월"**로 정했습니다 (실행한 달은 신고가 다 들어오지 않아 뺌).
2. 수집 스크립트(`collect_trades.py --end`, 기본 전월)와 적재 스크립트(`load_trades.py --end`)가 같은 기준을 쓰게 맞췄습니다.
3. 해제(취소)된 거래는 평균에서 빼도록 함께 확인했습니다.

### 해결 결과

- 다시 적재한 뒤 모든 면적대의 기간이 12개월 안에 들어왔습니다. 화면에 "최근 1년 거래 35건 (2025년 10월 ~ 2026년 9월)"처럼 기간을 함께 표시합니다.
- 재발 여부는 적재할 때마다 `data_collections`에 남는 기준일과 화면의 기간 표시로 확인합니다.
- 기간을 정하는 동안 PR이 다섯 번 오갔습니다: #25(13개월 반영) → #27(보여 주는 기간 12개월) → #28(평균은 12개월로) → #31(문서를 12개월로 되돌림) → #35(수집도 12개월). 수집 파일은 65개에서 60개로 맞췄고, 기간 밖 거래는 저장하되 평균에는 쓰지 않습니다.
- **남은 점:** 13개월로 넣었던 PC의 DB에는 2026-10 거래 188건이 `trades`에 남아 있습니다(평균에는 안 쓰임). 그래서 발표 자료의 17,268건과 12개월 기준 17,080건이 다릅니다.

### 재발 방지 방안

- **설정 · 코드 변경:** 두 스크립트의 기간 계산을 같은 규칙(전월까지 12개월)으로 통일, `--end`로 명시 가능
- **운영 점검 항목:** 갱신 후 `/api/data-status` 기준일과 아파트 정보의 집계 기간 확인 (운영 가이드 ⑥)
- **문서 업데이트:** 요구사항(FR-DATA-01), DB 설계서의 집계 기간 설명, CLAUDE.md "지역 이름과 코드"에 기간 규칙. 화면에는 "최근 1년"이라고만 씁니다.

## 2. 지도 확대 중 지도가 멈춤

- **발생 일시:** 2026-10-20
- **담당자:** 김해원 · 안세환
- **영향 범위:** 지도 화면 전체 (웹 · 모바일)

### 문제 상황

- 마우스 휠과 + − 버튼으로 빠르게 확대 · 축소하거나, 확대 도중 창 크기가 바뀌면 지도가 굳어 움직이지 않았습니다.
- 사용자는 새로고침해야 다시 쓸 수 있었습니다.
- 브라우저 콘솔에 같은 오류가 수천 번 쌓였습니다.

```
kakao.js:108 Uncaught TypeError: Cannot read properties of undefined (reading 'x')
2821 kakao.js:108 Uncaught TypeError: ...
```

### 원인 분석

- **직접 원인:** 카카오맵의 확대 애니메이션(`setLevel` + `animate`)이 끝나기 전에 다음 확대가 겹쳤고, 확대 도중 지도 크기 다시 맞추기(`relayout`)가 끼어들어 애니메이션 내부 값이 깨졌습니다. 깨진 애니메이션이 매 프레임 오류를 냈습니다.
- **근본 원인:** 외부 SDK의 애니메이션이 동시에 하나만 안전하다는 제약을 모르고, 여러 곳(휠 · 버튼 · 창 크기 · 아래 창)에서 각각 지도를 조작했습니다.
- **확인 방법:** 콘솔 스택이 카카오 SDK의 애니메이션 루프(`requestAnimationFrame`)에서 나오는 것을 확인하고, 확대 도중 `relayout`을 일부러 부르는 재현 시험을 했습니다.

### 해결 과정

1. 확대 요청을 한 줄로 줄 세웠습니다 (`animateZoom`): 확대가 진행 중이면 마지막 목표만 기억했다가 끝난 뒤 실행합니다.
2. 확대가 진행 중이면 `relayout`을 확대가 끝난 뒤로 미뤘습니다 (`ensureMapSize`).
3. 확대 기준점이 잘못된 값이거나 지도가 숨어 있으면 애니메이션 없이 수준만 바꿉니다.

### 해결 결과

- 같은 동작(빠른 휠 · + − 20번 연타 · 카드 빠르게 바꾸기 · 확대 중 창 크기 변경)을 자동 점검으로 다시 해 봐도 콘솔 오류 0건, 지도가 멈추지 않았습니다 (35da19a, #148).

### 재발 방지 방안

- **설정 · 코드 변경:** 지도 확대는 반드시 `animateZoom`을 거치도록 함, 크기 맞추기는 `ensureMapSize` 한 곳에서만
- **운영 점검 항목:** 지도 관련 배포 전 "빠르게 확대 · 축소 + 창 크기 변경" 수동 점검
- **문서 업데이트:** `frontend/js/map-view.js` 주석에 카카오 애니메이션 제약 기록

## 3. 고친 화면이 반영되지 않음 (브라우저 캐시)

- **발생 일시:** 2026-10-16 ~ 10-20
- **담당자:** 박채은 · 김해원
- **영향 범위:** 모든 화면

### 문제 상황

- CSS · JS를 고쳐 머지했는데, 팀원과 사용자 화면에는 예전 모양이 그대로 보였습니다.
- 서로 다른 화면을 보면서 버그를 이야기하게 되어 확인에 시간이 걸렸습니다.
- 예전 `format.js`가 캐시에서 열려 지도가 멈춘 적도 있습니다 (7d3f72e, 10-13).
- 오류 메시지는 없었습니다. Network 탭에서 파일이 `(disk cache)`로 열리는 것을 확인했습니다.

### 원인 분석

- **직접 원인:** 브라우저가 같은 주소의 CSS · JS 파일을 캐시에서 꺼내 썼습니다.
- **근본 원인:** 파일이 바뀌어도 주소가 같아, 브라우저가 바뀐 것을 알 방법이 없었습니다.
- **확인 방법:** 강력 새로고침(Ctrl + Shift + R)을 하면 새 화면이 보이는 것으로 확인했습니다.

### 해결 과정

1. HTML 응답에 `Cache-Control: no-cache`를 붙여 화면 파일은 항상 새로 확인하게 했습니다 (10-16).
2. HTML이 부르는 CSS · JS 주소 뒤에 버전 번호(`?v=20261020-43`)를 붙이고, 파일을 고칠 때마다 숫자를 올리는 규칙을 만들었습니다.
3. 버전이 붙은 CSS · JS는 1일 캐시, gzip 압축을 걸었습니다 (`backend/main.py`).

### 해결 결과

- 배포 뒤 새로고침 한 번에 반영됩니다.
- 전송량도 줄었습니다: `map-view.js` 182KB → 55KB (약 70% 감소).

### 재발 방지 방안

- **설정 · 코드 변경:** HTML no-cache, 버전 붙은 정적 파일 1일 캐시 + gzip
- **운영 점검 항목:** PR 검토 때 "CSS · JS를 고쳤으면 `?v=`를 올렸는가" 확인 (운영 가이드 ⑦)
- **문서 업데이트:** `CLAUDE.md`에 "JS · CSS를 고치면 그 화면 HTML의 `?v=` 숫자를 올린다" 규칙 추가

## 4. 여러 명이 같은 파일을 고쳐 충돌 표시가 커밋됨

- **발생 일시:** 2026-10-20
- **담당자:** 안세환
- **영향 범위:** 지도 화면(`frontend/map.html`)

### 문제 상황

- 지도 화면 하나에 지도(안세환) · 목록(김목산) · 시나리오 · 웹 배치(박채은)가 함께 들어가면서, 같은 `map.html`의 버전 번호 줄을 동시에 고쳤습니다.
- 충돌을 푸는 머지 커밋이 10번(그중 `map.html` 8번) 생겼습니다 (#58 #63 #132 ~ #139 #141).
- 병합 중 생긴 충돌 표시(`<<<<<<<`, `=======`)가 그대로 커밋되어, 그 브랜치에서는 화면이 깨졌습니다.

### 원인 분석

- **직접 원인:** 오래된 `develop` 위에서 작업하다 늦게 합치면서, 충돌을 손으로 풀다 표시를 남겼습니다.
- **근본 원인:** 작업 시작 전에 최신 `develop`을 받는 습관과 확인 절차가 없었습니다.
- **확인 방법:** PR의 변경 파일에서 충돌 표시를 발견했습니다.

### 해결 과정

1. 충돌 표시를 지우고 버전 번호를 양쪽 변경에 맞게 정리했습니다 (`fix: map.html 충돌 표시 지우고 버전 맞춤`).
2. 파일별 담당 원칙(`docs/roles.md`): 남의 파일을 고칠 때는 먼저 담당에게 알립니다.
3. 팀원용 "develop 받기" 안내서를 만들어 아침마다 최신화하는 순서를 정했습니다.
4. PR은 1명 이상 승인 후 머지합니다.
5. `?v=`는 "둘 중 큰 숫자, 또 고쳤으면 하나 더"로 정하고, PR 설명에 머지 순서를 적습니다 ("이 PR은 #132 다음에 머지").

### 해결 결과

- 이후 충돌은 PR 단계에서 잡혔고, `develop`에 충돌 표시가 들어간 일은 다시 없었습니다. 전체 PR은 164개 병합했습니다 (2026-10-26 기준).

### 재발 방지 방안

- **설정 · 코드 변경:** 브랜치 규칙 `main` / `develop` / `feature`, `main` · `develop` 직접 push 금지
- **운영 점검 항목:** PR 검토 때 충돌 표시 검색, `develop`과 충돌 여부 확인
- **문서 업데이트:** `docs/git_rule.md`, `docs/guides/notice_sync_develop.md`

- **영향 범위:** 배포 주소로 접속한 모든 사용자 (로컬은 정상)

### 문제 상황

- 로컬(`localhost:8000`)에서는 지도가 뜨는데, 외부 공개 주소에서는 지도 자리에 "지도를 불러오지 못했습니다"가 나왔습니다.
- 목록과 계산은 정상이었습니다.

### 원인 분석

- **직접 원인:** 카카오맵 SDK가 요청한 도메인을 거부했습니다.

```
GET https://dapi.kakao.com/v2/maps/sdk.js?appkey=... 401
{"errorType":"AccessDeniedError","message":"domain mismatched! caller=https://....trycloudflare.com. check out registered web domains."}
```

- **근본 원인:** 카카오맵 JavaScript 키는 카카오 개발자 콘솔에 등록한 사이트 도메인에서만 동작합니다. 새 공개 주소를 등록하지 않았습니다.
- **확인 방법:** 같은 SDK 주소를 공개 주소를 `Referer`로 붙여 직접 요청해 401 응답 본문을 확인했습니다. 서버 자체(`/map.html`)는 200이었습니다.

### 해결 과정

1. 카카오 개발자 콘솔 → 앱 설정 → 플랫폼 → Web → 사이트 도메인에 공개 주소를 추가했습니다.
2. 임시 터널은 다시 켤 때마다 주소가 바뀌어, 고정 주소가 있는 무료 호스팅(Render)으로 옮겼습니다.

### 해결 결과

- 배포 주소 `https://money-to-home.onrender.com/`에서 지도가 정상 표시됩니다.

### 재발 방지 방안

- **설정 · 코드 변경:** 고정 도메인(Render) 사용
- **운영 점검 항목:** 주소가 바뀌면 카카오 도메인 등록 (운영 가이드 ⑧의 6번)
- **문서 업데이트:** README 배포 절에 "카카오 사이트 도메인에 배포 주소 등록" 추가

## 7. 스크롤바 수정 후 화면이 멈춤

### 원인 분석

- **직접 원인:** 화면 속성 변화를 감지(`MutationObserver`)해 손잡이 위치를 다시 맞추는데, 손잡이 자신도 위치를 맞추며 자기 `class`를 바꿨습니다. 그 변화를 다시 감지하는 일이 끝없이 반복되어 브라우저가 멈췄습니다.
- **근본 원인:** 감지 대상에서 자기 자신을 빼지 않았습니다.
- **확인 방법:** 손잡이가 보일 때만 멈추고, 감지 코드를 빼면 정상인 것으로 범위를 좁혔습니다.

### 해결 과정

1. 감지된 변화가 손잡이 자신의 것이면 무시하도록 고쳤습니다 (`frontend/js/scrollbar.js`).
2. 버전 번호를 올려 바로 배포했습니다.

### 해결 결과

- 손잡이를 띄운 채 목록을 접었다 펴도, 휠로 스크롤한 뒤 클릭해도 정상 동작했습니다.

### 재발 방지 방안

- **설정 · 코드 변경:** 변화 감지 코드는 자기가 바꾸는 요소를 감지 대상에서 뺌
- **운영 점검 항목:** 화면 공통 스크립트를 고치면 배포 전 "스크롤 → 클릭" 수동 점검

- **발생 일시 · 담당:** 2026-10-15 · 김목산 (#104)
- **원인:** 이어 가기가 첫 입력 화면으로만 보냈습니다.
- **해결:** 넣은 값이 다 있으면 바로 지도로 가고, 입력 요약에 "수정하기"를 더했습니다. 로그인한 뒤에는 보던 화면으로 돌아갑니다.

## 21. 배포 서버의 클라우드 DB 접속

- **발생 일시 · 담당:** 2026-10-22 · 김해원 (#163 #164)
- **상황:** 배포(Render) 서버는 로컬 MariaDB가 아니라 클라우드 MySQL(Aiven)에 접속해야 했습니다.
- **원인:** 클라우드 DB는 암호화(SSL) 접속을 요구하지만, 로컬용 설정에는 SSL이 없었습니다.
- **해결:** `DB_SSL=true`면 암호화 접속, `DB_SSL_CA`가 있으면 서버 인증서도 확인합니다. 비워 두면 지금처럼 로컬에 접속합니다. 서버와 적재 스크립트에 모두 적용했습니다.
- **재발 방지:** 접속 정보 · 인증서는 코드가 아니라 환경 변수(`.env`, Render 설정)에만 둡니다 (운영 가이드 ①).
