# Git 협업 규칙

| 항목 | 내용 |
| --- | --- |
| 대상 | 팀원 전원 |
| 읽는 시간 | 5분 |
| 먼저 끝낼 것 | `docs/setup_guide.md`, `docs/pr_practice.md` |

## 규칙 두 가지

1. **작업을 시작하기 전에 `develop`에서 `git pull`을 한다.**
2. **`develop`에는 PR로만 넣는다. 팀장이 검토하고 합친다.**

나머지는 이 두 가지를 지키는 방법이다.

## 브랜치

| 브랜치 | 쓰임 | 직접 올리기 |
| --- | --- | --- |
| `main` | 발표할 완성본 | 안 된다 |
| `develop` | 모두의 작업이 모이는 곳. 기준 브랜치 | 안 된다 |
| `feature/이름` | 각자의 작업 | 된다 |

브랜치 이름과 커밋 메시지의 앞머리

| 앞머리 | 쓰는 때 | 브랜치 예 | 커밋 예 |
| --- | --- | --- | --- |
| `feature` / `feat` | 기능을 새로 만든다. | `feature/loan-calc` | `feat: 대출 계산 함수 추가` |
| `fix` | 오류를 고친다. | `fix/loan-rounding` | `fix: 월 상환액 반올림 오류 수정` |
| `docs` | 문서를 고친다. | `docs/api-spec` | `docs: API 명세서 A-05 응답 수정` |
| `chore` | 설정, 정리 | `chore/gitignore` | `chore: .gitignore에 로그 폴더 추가` |
| `refactor` | 동작은 그대로 두고 코드를 정리한다. | `refactor/calc` | `refactor: 계산 함수 이름 정리` |

브랜치 이름은 영어 소문자와 `-`만 쓴다.

## 작업 한 번의 순서

### 1. 최신 내용을 받는다

```
git checkout develop
```

```
git pull
```

### 2. 작업 브랜치를 만든다

```
git checkout -b feature/작업이름
```

### 3. 작업한다

돌려 보고 되는 것을 확인한다.

### 4. 바뀐 것을 본다

```
git status
```

자기가 고친 파일만 보여야 한다. **`.env`가 보이면 멈추고 팀장에게 알린다.**

### 5. 담고 기록한다

```
git add 고친파일
```

```
git commit -m "feat: 무엇을 했는지"
```

`git add .`은 쓰지 않는다. 파일 이름을 적어 담는다.

### 6. 올린다

```
git push -u origin feature/작업이름
```

### 7. PR을 연다

1. GitHub에서 **Compare & pull request**를 누른다.
2. **base가 `develop`인지 확인한다.** `main`이면 바꾼다.
3. 설명 칸에 무엇을 했는지, 어떻게 확인했는지 적는다.
4. **Create pull request**를 누른다.
5. 단체방에 "PR 올렸습니다"라고 알린다.

### 8. 합쳐지면 받는다

```
git checkout develop
```

```
git pull
```

다음 작업은 1번부터 다시 한다.

## 명령의 뜻

| 명령 | 뜻 |
| --- | --- |
| `git checkout develop` | `develop` 브랜치로 옮겨 간다. 폴더 안의 파일이 그 브랜치의 내용으로 바뀐다. |
| `git checkout -b 이름` | 새 브랜치를 만들고 그리로 옮겨 간다. |
| `git pull` | 지금 있는 브랜치의 최신 내용을 GitHub에서 받는다. |
| `git status` | 지금 어느 브랜치인지, 무엇이 바뀌었는지 본다. |
| `git add 파일` | 올릴 파일을 담는다. |
| `git commit -m "글"` | 담은 것을 기록으로 남긴다. |
| `git push` | 기록을 GitHub에 올린다. |

지금 어느 브랜치에 있는지는 VS Code 왼쪽 아래 구석에서도 보인다.

## PR 설명에 적을 것

```
## 한 일
- 

## 확인한 방법
- 

## 봐 주면 좋은 곳
- 
```

## 검토 (팀장)

PR의 **Files changed** 탭에서 본다.

| 번호 | 확인할 것 | 이유 |
| --- | --- | --- |
| 1 | base가 `develop`이다. | `main`으로 잘못 여는 일이 가장 흔하다. |
| 2 | 자기 담당 파일만 고쳤다. | 남의 파일을 고치면 충돌이 난다. |
| 3 | `.env`와 키 값이 없다. | 한 번 올라가면 기록에 남는다. |
| 4 | 계산식이 화면 코드에 없다. | 계산은 계산 모듈에만 둔다. |
| 5 | 금액이 원 단위 정수다. | 만원과 섞이면 10,000배 틀린다. |
| 6 | 돌려 봤다고 적혀 있다. | 안 돌려 본 코드가 합쳐지면 모두가 막힌다. |

| 결과 | 누르는 것 |
| --- | --- |
| 괜찮다 | **Review changes > Approve**, 이어서 **Merge pull request** |
| 고칠 것이 있다 | **Review changes > Request changes**. 고칠 점을 적는다. |

- 고쳐 달라는 말을 들으면 **같은 브랜치에서** 고치고 다시 `git push` 한다. PR에 자동으로 반영된다. PR을 새로 열지 않는다.
- 합친 사람은 단체방에 "○○ 합쳤습니다"라고 알린다. 들은 사람은 `git pull`을 한다.
- 팀장의 PR은 팀원 한 명이 검토한다. 팀장이 자리에 없을 때의 검토도 그 사람이 맡는다.

| 역할 | 담당 |
| --- | --- |
| 검토와 머지 | 김해원 |
| 팀장 PR 검토, 팀장 부재 시 검토 | |

## 지킬 것

- 새 작업은 항상 `develop`에서 `git pull`을 한 뒤 시작한다. 이전 작업 브랜치에 머문 채 새 브랜치를 만들면 예전 작업이 딸려 들어간다.
- PR은 작게, 자주 보낸다. 기능 하나가 돌아가면 보낸다. 하루 한 번 이상이 좋다.
- 자기 담당 파일만 고친다. 공통 파일을 고쳐야 하면 만든 사람에게 먼저 말한다.
- 키와 비밀번호는 `.env`에만 둔다.
- 올리기 전에 직접 돌려 본다.

## 작업 중에 `develop`이 바뀌었을 때

다른 사람의 PR이 합쳐졌다는 알림을 들으면, 작업 브랜치에서 아래를 실행해 따라잡는다. 미룰수록 충돌이 커진다.

```
git pull origin develop
```

## 막히면

| 상황 | 할 일 |
| --- | --- |
| `CONFLICT`가 나온다. | 두 사람이 같은 곳을 고쳤다. 혼자 풀지 말고 그 파일의 담당자와 같이 본다. |
| `develop`에서 바로 작업해 버렸다. (커밋 전) | `git checkout -b feature/작업이름`을 하면 고친 내용이 새 브랜치로 따라온다. |
| 엉뚱한 브랜치에 커밋했다. | 더 진행하지 말고 팀장에게 알린다. |
| `.env`를 올려 버렸다. | 바로 팀장에게 알린다. 키를 새로 발급받아야 한다. |
| `403`, `Permission denied` | 저장소 권한이 없다. 팀장에게 GitHub 아이디를 알려 준다. |
| 무엇을 눌렀는지 모르겠다. | `git status` 결과를 캡처해 팀장에게 보낸다. |

## `develop`을 `main`에 합칠 때 (발표 전에 한 번)

2026-10-12에 작업 전체가 실수로 `main`에 합쳐졌다가 되돌려졌다 (PR #10, #11). Git은 그날까지의 커밋을 `main`이 이미 받은 것으로 기억한다. 그래서 `develop`을 `main`에 그냥 합치면 **그날까지의 작업이 들어가지 않는다.**

`main`에 합치기 전에 되돌리기 커밋(`4e5e1a4`)을 먼저 되돌린다. 팀장이 한다.

1. `main`에서 새 브랜치를 만들어 `git revert -m 1 4e5e1a4`를 하고 `main`으로 PR을 보내 합친다.
2. 그다음 `develop`을 `main`으로 보내는 PR을 합친다.

## 하지 말아야 할 것

- `main`과 `develop`에 직접 올리지 않는다.
- `git push --force`, `git reset --hard`를 쓰지 않는다. 다른 사람의 작업이 사라질 수 있다.
- 모르는 명령을 인터넷에서 찾아 그대로 실행하지 않는다. 먼저 팀장에게 묻는다.
